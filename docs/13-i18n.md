# 13. Internationalisation

Every word a player reads, where it comes from and which language it comes out in. Nineteen
javadoc comments point here; this document is written from them.

## 13.1 A message is a key, never a literal

Every player-facing string resolves through a `MessageKey`. There are no inline literals
anywhere in this codebase, and `NoInlineUserMessageDriftTest` fails the build over one.

A key carries its catalogue lookup string and nothing else. The constant is the handle and
the catalogue is the registry, which is what keeps the enums immutable and what lets a new
language arrive as a file rather than as a Java change.

## 13.2 The naming maps one to one

The enum constant is `UPPER_SNAKE` and the catalogue key is kebab-case, dot separated:
`HOME_NOT_FOUND` is `home.not-found`. The mapping is a convention with a guard behind it
rather than a habit.

## 13.3 Twelve languages ship

`en`, `tr`, `de`, `ru`, `es`, `pt`, `fr`, `pl`, `uk`, `zh`, `ja` and `ko`, each as
`messages/messages_<lang>.conf`, written into the data folder on first run and edited there.
Nothing counts them: a thirteenth language is a thirteenth file.

## 13.4 Which language a viewer gets

One deterministic chain, first hit wins.

1. The player's persisted `/lang` override. An explicit choice always beats the client.
2. The locale bound for this request at the command boundary: the client locale, captured on
   the region thread and carried across async hops, so a message deferred to a worker still
   comes out in the requester's language.
3. The configured server default, for a path that never crossed the boundary, such as an
   event driven broadcast with no requesting command.
4. English, the canonical root.

The resolver itself never calls the Bukkit API. `Player.locale()` is a region-thread call
captured once at the boundary, so resolution works on any thread.

One layer below this, a key missing from a catalogue falls back to the English wording for
that key only, not for the whole message.

## 13.5 The locale is bound at the inbound boundary

Every published command is wrapped by one shared binding that resolves the requesting
player's locale and puts it in the request-scoped carrier before any handler runs. It is a
chokepoint on purpose: a handler cannot forget to do it, and a use case never asks the server
anything to find out which language to speak.

## 13.6 A disabled module still ships its keys

One registry enumerates the per-module key enums, `shared` first. It is whole regardless of
which modules are enabled at runtime, because a catalogue with holes in it depending on a
server's configuration would make the parity guard mean nothing and would leave a translator
guessing.

Each context owns its own enum: teleport owns the teleport keys, economy the wallet keys. A
context therefore names its own keys with no cross-context dependency, and adding a new
context's enum to the registry is the one edit a new module makes to join the parity matrix.

## 13.7 `/lang`, `/help`, and where the preference lives

`/lang` is the per-player override and `/help` is the cross-cutting command listing. Neither
belongs to a feature context, so both are owned by the kernel.

The override is stored in the player's PDC, so it survives a relog with no database round
trip. A lost language preference is harmless and does not need to survive a world rollback
the way a balance does, which is exactly the rule in `03-paper-api.md` §3.6.

## 13.8 Two ways a message reaches a player

### 13.8.1 Resolved here

The normal path. The catalogue resolves the key for the viewer's locale, MiniMessage parses
the result once, and the component is delivered on the viewer's own thread.

### 13.8.2 Handed to Adventure as a translatable

Every catalogue key is also registered with Adventure's `GlobalTranslator`, so a component
built with a translatable key renders in the viewer's language wherever Adventure does the
rendering. It is the same catalogue behind both paths, so the two cannot disagree.

## 13.9 What a translator may and may not change

The words, all of them, and the MiniMessage tags inside them. Not the key, not the
placeholder names, and not the shared `<prefix>` tag, which the sink supplies rather than
each template inlining it.

## 13.10 The guards

### 13.10.1 No inline text

A user-facing string that is not a key fails the build.

### 13.10.2 Locale parity

Every `messages_<lang>.conf` declares exactly the key set `messages_en.conf` declares, which
in turn equals the `MessageKey` constants, checked in both directions. English is the
authority: a hole left by an English change and a stale key left by a rename both fail.

It runs as its own task ahead of the test phase and exits non-zero with the offending keys
named, so a missing translation is found in seconds rather than after the whole suite.
`04-build.md` §8.1 has the mechanism.
